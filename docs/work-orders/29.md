# Work order #29 — tech: int4 model cut needs an ORT upgrade (blocked on onnxruntime 1.17 — see #28)
> milestone: v14 — polish & perf · branch: `feat/issue-29`

## Acceptance criteria (from the issue)

**Follow-up to #28** — int4 model cut. Blocked on ORT 1.17 (proven); **feasible on ORT 1.27 (proven)**.

**PROVEN 2026-08-11 (not guessed):** I downloaded `onnxruntime-web@1.27.0` and inspected its WASM binary. It contains the full int4 kernel family:
- `INT4` / `UINT4` tensor types (in the type enum)
- `ApplyMatMulNBits`, `DirectDQFusedMatMulNBits`, `DQMatMulNBitsFusion`, `DP4AMatMulNBits`, `DQMatMulToMatMulNBits`
- `Explicit qdq_matmulnbits_block_size must be a power-of-2` (block-wise int4 QDQ) + `GetPackedUint4Element`
- `DequantizeLinear` opset versions 10/13/19/21/23/24/25 (the opset-21 int4 path is there)
By contrast, the pinned **1.17.0** WASM had **zero** int4 symbols — that's why int4 was blocked. The path forward is a **clean swap of the ORT bundle only** (piper-wasm 0.1.4 worker + phonemizer stay; just replace `ort.min.js` + the `.wasm` files with 1.27.0 equivalents and keep `numThreads=1`).

**Goal:** Bangla model ~20MB int8 → ~10MB int4 → cold first-run `neural.ready` ~4–5s total (was ~6–7s after #28's gzip).

**Acceptance criteria**
- [ ] **Swap ORT bundle → 1.27.0** in `infra/deploy/scripts/fetch_voice_assets.sh` (keep the single-thread patch — `numThreads=1`, no COOP/COEP). The 1.20+ layout change (only `ort-wasm-simd-threaded*.wasm` ship — no plain `ort-wasm-simd.wasm`) is **de-risked**: the 1.27 loader forces `numThreads=1` when multi-threading is unsupported (no SAB/COOP-COEP) and runs the `-threaded` wasm single-threaded — **proven by running the int4 model through the actual 1.27 browser wasm binary in Node** (`run_ort_wasm.js`, all 3 phrases synth valid audio in 381–650ms). Remaining: rewire `fetch_voice_assets.sh` to the 1.27 files, verify the piper worker initializes with the new bundle, live-browser check.

**Verification evidence (2026-08-11, bounded docker container `python:3.12-slim`, `--memory 2g --cpus 2`, ORT 1.27.0):**
- 138 Conv/ConvTranspose weights quantized block-wise (block 32 along dim 1, per-position scale, symmetric → zp omitted, opset 21): **75.7 MB → 11.9 MB** weights; on-disk **76.8 MB fp32 → 13.0 MB**.
- Opset-15→21 migration needed: ReduceMean/ReduceMax/etc. move `axes` attr → input (72 migrated); int4 tensor types need opset 21 + IR 10. Fixed in `quantize_int4`.
- ORT blocked-DQ demands scale/zp at the input's FULL RANK (`scale.Shape()[i] == ceil(Di/block_size)` on the axis, every other dim unchanged) — proven from `quantize_linear.cc` (v1.27.0, `PrepareForQDQ`/blocked dequant loop). Per-position scales within each block.
- **Full graph load + synth OK** (encoder→decoder→vocoder, valid waveform `[1,1,1,N]`). Sizes proven: `fp32 76.8 -> int4 13.0 MB`.
- **Quality signal:** with production scales `[0.667, 1.0, 0.8]`, int8 (shipped) vs int4 durations match within ±256 samples (1–2%) on 5/6 phrases; fp32 vs int4 deviate up to ±10% — the duration predictor is the sensitive spot (int8 shares the same fp32 drift, so it's inherent to weight-only quantization, not int4-specific). Waveforms differ between int8/int4 (different quantization granularity) → **subjective listen gate still required.**
- **QA artifacts for the human gate:** on the box at `/tmp/qa/` — `int8_*.wav` (shipped baseline) vs `int4_*.wav` (native ORT 1.27) vs `wasm_int4_*.wav` (**the actual 1.27 browser-wasm kernel path**) A/B sets for ঠিক আছে, নোট, এক দুই তিন, বাংলা শোনো (real phonemes via espeak-ng `--ipa=1` greedy-matched to `phoneme_id_map`, production scales `[0.667,1.0,0.8]`, 22050 Hz, 16-bit PCM).
- **Browser-wasm run evidence (`run_ort_wasm.js`):** `ort-wasm.min.js` 1.27 + `ort-wasm-simd-threaded.wasm`, `numThreads=1`, int4 model loaded from bytes — ঠিক আছে 24832 smp/650ms, নোট 13824/381ms, এক দুই তিন 20480/547ms; all finite, peak |v| 0.2–0.6 (real audio). Note: native-vs-wasm runs of the same int4 model can produce different durations (VITS prior noise + kernel numerics) — reinforces the human listen gate.
