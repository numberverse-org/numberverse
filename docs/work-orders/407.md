# #407 — Parent-area cleanup: no Class Insights on user face, ONE parent page, real portal security

**Status:** in progress (2026-08-12)

## Problem

> "'Class Insights' is by default on , No need show on user face. Still 2 page for
> parent in User Face app , Also no security to access parent portal by kids"

Three concrete issues after #405/#406:

1. **Class Insights still shows** on the user face (and looked "on by default") —
   the Kotha aggregate opt-in + preview card lived in the signed-in parent panel.
2. **Two parent pages** in the user-face app — the full-page `parentgate` screen
   AND the `parent` panel. A kid could hit either; one entry path never told you
   which.
3. **Parent portal had NO security** — `apps/parent/app/page.tsx` rendered the
   dashboard on token *presence* (`localStorage.getItem("nv_parent_token")`), no
   server-side validation. The kid app writes the SAME localStorage key, so a kid
   (or a stale/forged token) could open `/parent/` and see the full dashboard.

## Fix

### 1. Class Insights removed from the user face entirely
- Deleted the `settings-aggregate-card` JSX from the parent panel (opt-in button,
  aggregate preview, opt-out, offline note).
- Removed `aggOpted`/`agg`/`aggBusy` state, `loadAggregates`, and the refresh
  `useEffect`.
- Removed the 12 agg* keys from the `Strings` interface + EN + BN dicts.
- Removed the unused imports (`aggregateOptIn`, `setAggregateOptIn`,
  `fetchAggregates`, `KothaAggregates`) from App.tsx.
- Removed the dead `.settings-aggregate-card` / `.agg-*` CSS.
- `apps/kid/src/api.ts` keeps `aggregateOptIn`/`setAggregateOptIn`/`fetchAggregates`
  + `KothaAggregates` (the server model still has the field) — just no UI.

### 2. ONE parent page in the user face
- Deleted the entire `parentgate` screen (JSX + `"parentgate"` in the `Screen` type).
- The single `screen === "parent"` page now shows the sign-in form **inline**
  when `!hasParentSession()`, otherwise the full signed-in parent panel.
- All 4 routing sites updated: initial screen, session-validation bounce,
  `goParent()`, `signOut()`, welcome/syllabus sign-in links → all land on
  `"parent"`.
- Removed the now-redundant defense-in-depth effect (the inline gate makes the
  parent page itself the gate — a kid tapping "For parents" sees the login form,
  never any parent data).

### 3. Parent portal security — real server-side gate
- New `validateToken(token)` in `apps/parent/lib/api.ts` — three-way check via
  `GET /auth/me`: `"ok"` (2xx), `"invalid"` (401/403), `"offline"` (network/5xx).
- `apps/parent/app/page.tsx` — `authState: "checking" | "ok" | "anon"` gate.
  On mount the stored token is validated **before** the dashboard renders:
  - `ok` → dashboard loads (refreshAll + reloadAccount).
  - `invalid` → token + parent keys cleared, login gate with
    "Your session ended. Sign in again."
  - `offline` → login gate with "Can't check your session right now…", stored
    token kept so a reload re-validates when back online.
  - No token at all → login gate.
- The dashboard can never render with an unvalidated token. A kid with a shared,
  stale, or forged `nv_parent_token` lands on the login page, not on parent data.

## Files
- `apps/kid/src/App.tsx` — aggregate card/state/strings removed, `parentgate`
  deleted → single `parent` page with inline gate, imports cleaned
- `apps/kid/src/styles.css` — `.settings-aggregate-card` + `.agg-*` removed
- `apps/parent/app/page.tsx` — authState gate, server-side token validation,
  login/checking shells
- `apps/parent/lib/api.ts` — `validateToken()` helper
