# #139 — Physical flashcards QR → mini game tie-in

**Status:** ✅ done (PR pending → issue CLOSE)

## Problem

A parent wants to print physical flashcards that open the matching mini-game.
Acceptance: **QR generator** + **no network required** (offline-first).

## Fix

QR codes encode the game a card belongs to (`NV:<skillId>`) and are 100%
client-side — nothing leaves the browser, and opening a card never needs a
network.

**Generator** (`apps/parent` — the print surface):
- New **"🎴 Flashcard QR cards"** card (beside the #132 worksheet card): for
  the active kid's PLAYED skills, it builds a printable A4 sheet of QR cards
  (skill title + QR + the human-readable `NV:…` code). Generation is pure
  client-side via `qrcode` (no server, no API). Print via the browser's
  dialog with a dedicated print-only `.qr-grid` layout (3-per-row, dashed
  cut lines).

**Reader** (`apps/kid` — the scan side):
- New **📷 Scan a card** button on the play screen (top row, next to
  settings). Opens a scan sheet that auto-starts the camera
  (`getUserMedia`, rear camera) and live-decodes QRs with `jsQR` (dynamically
  imported so the main bundle stays lean). A decoded `NV:<skillId>` resolves
  through the catalog and launches that skill's mini-game via the existing
  `startSingleSkill` — at the kid's own adaptive level.
- **Offline / no-camera fallback**: if the camera is denied/unavailable (or
  the page isn't a secure context), the sheet falls back to a **manual code
  entry** input (`NV:skillId` or bare `skillId`) — so the card→game path is
  fully functional and locally gateable without a device camera. Unknown codes
  show a friendly error and never crash.
- Camera capture itself needs a physical device to verify (standing rule:
  testing on the operator's own devices only) — the manual path is the
  pipeline-verified route; the decode loop reuses the same launcher.

## Files
