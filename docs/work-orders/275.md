# #275 — Safety: age-appropriate band lock for content

**Status:** 🚧 in progress (feature branch `feat/issue-275`)

## Problem

The client locked worlds above the parent's `max_band`, but the API accepted
ANY progress/story event — a tampered client (or a stale cached skill list)
could persist progress and learning stories for content the parent had capped.

## Done-when (from the issue)

- [x] **Server check** — `/progress` and `/stories` now drop events whose skill
      band exceeds the kid's `max_band`. An unknown skill + a cap fails closed
      (we can't prove it's age-appropriate → blocked). Response reports
      `band_skipped` (client ignores the field — backward compatible).
- [x] **Client check** — already present (`worldUnlocked` locks worlds above
      the cap); unchanged.
- [x] **Settings respected** — the server's `PUT /settings` already validates
      `max_band` ∈ 1..5 (`ge=1, le=5`); the effective cap is read from the live
      `kid_settings` row each batch (one query), so a parent's change applies
      to the very next sync.
- [x] **Test matrix** — `test_band_lock.py`: 18 checks across
      {cap: none/1/2/5} × {band: 1/2/5/unknown} + boundary + empty-map edge.
      Dependency-free (no DB), runs in the CI `api` job.

## Design

- `apps/api/app/bandlock.py` — the pure rule `skill_band_allowed(skill_id,
  band_map, max_band)`, dependency-free so it's unit-testable in CI.
- `progress.py` — `SKILL_BANDS` built from the seed catalog (the audit gate
  already keeps seed ⇄ core skills in sync); `_load_band_caps` reads each
  kid's cap once per batch; both write endpoints filter through it.
- Dropping (not 400ing) keeps the sync loop simple: a tampered batch records
  the allowed events and silently skips the rest.

## Files
