# #131 — Multi-language scaffold (Arabic/Hindi) — research

**Status:** ✅ done (merged — issue CLOSED; architecture shipped)

## Problem

Evaluate the i18n cost of adding Arabic/Hindi to the existing EN/BN table,
without scope creep.

## Done-when (from the issue)

- [x] **Spike doc with estimates** — `docs/I18N_SCAFFOLD.md`: the full cost
      breakdown (engine = 1-3 engineering days per language; content/curriculum
      = the real, data-driven cost), RTL plan, digit handling, curriculum-pack
      design, and the "never ship a partial language" guardrail.
- [x] **No scope creep** — ar/hi are registered as `status: "planned"`
      scaffolds only; the audit enforces parity ONLY for shipped locales (en/bn),
      so a partial translation can never silently ship.

## The architecture (what made the estimates real)

- `packages/core/src/locale.ts` — the `LocalePack` registry (code, dir, digits,
  localeTag, curriculum, voice, status) + `formatNumber` + `isRtl` +
  `shippedLocales()` — pure + dependency-free, CI-tested.
- `apps/kid/src/game/locale.ts` — `getLocale()` returns the active pack.
- `apps/kid/src/game/i18n.ts` — `DICTS` table; `t()` resolves by locale code;
  unknown codes fall back to EN (never a raw key to a child).
- `apps/kid/src/App.tsx` — `documentElement.dir` flips to `rtl` for Arabic.
- `apps/kid/src/game/speech.ts` — future locale codes fall back to en until
  their voice lands (speech never receives an unsupported code).
- `apps/kid/scripts/audit.mjs` — i18n parity now iterates EVERY shipped locale.
- `scripts/test-locale.mjs` — CI gate, 18 checks.
