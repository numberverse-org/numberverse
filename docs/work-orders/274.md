# #274 — Guardrail: rate-limit on story + progress endpoints

**Status:** in progress (2026-08-13)

## Problem

The kid app's write endpoints — `POST /api/v1/progress` and
`POST /api/v1/stories` — had NO request-rate enforcement. Admin had a
*monitor* for the story rate (STORY_RATE_LIMIT_PER_HOUR, alert-only) but the
endpoint itself accepted unlimited batches. A stolen/leaked parent token, or
a buggy client, could bulk-replay story/progress batches with nothing to stop
it (DB growth, embed-job cost).

## Fix

- New `apps/api/app/ratelimit.py` — a dependency-free, in-memory sliding-window
  limiter keyed on `profile.id : client-ip`. No Redis/DB needed (single
  container). Sliding window (60s) with FIFO expiry; a global sweep caps map
  growth at 10k keys.
- Wired as `WRITE_RATE_LIMIT = rate_limit()` (default 120 req/min/account) into
  `record_progress` and `record_stories`. Depends on `get_current_profile`
  (cached per-request by FastAPI) so auth still runs exactly once. Breach → 429.
- Real cadence is ~2 req/min per account (kid syncs every 30s) — 120/min is
  >60× headroom; scripted bulk replay is capped.

## Files
- `apps/api/app/ratelimit.py` — new limiter module
- `apps/api/app/routers/progress.py` — wire into `/progress` + `/stories`

## Verification
- `python3 -m compileall -q apps/api/app` ✓
- Algorithm brute-forced: instant burst of `limit` allowed then 121st blocked;
  60s-window invariant never violated; real cadence never throttled ✓
