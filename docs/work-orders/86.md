# #86 — Parent: PIN lock to enter parent area

**Status:** 🚧 in progress (feature branch `feat/issue-86`)

## Problem

A kid handed a **signed-in** device could tap "Open parent area" and walk
straight into the parent panel — one more tap and they're in the full Parent
Portal. The sign-in form was the only barrier, and the parent had already
cleared it.

## Done-when (from the issue)

- [x] **Set / changed PIN flow** — mandatory 4-digit setup on the first signed-in
      panel entry; a "🔐 PIN lock" card on the panel opens the change flow
      (current PIN → new PIN → confirm).
- [x] **Wrong-PIN feedback** — each wrong try shows "Wrong PIN — N tries left";
      after 3 strikes the pad locks (brute-force blocked).
- [x] **Recovery hint for parents** — "Forgot PIN?" (arm → confirm) resets the
      lock and signs out; signing back in lands on a fresh-PIN setup.

## Design

The gate is enforced **inline on the parent screen render**, so *every* path to
the panel — `goParent`, a fresh sign-in landing back on `parent`, a session
restore — runs through it. There is no bypass path.

- `goParent` re-arms the gate (`setPinOk(false)` + a fresh pad) every time the
  parent area opens, so a kid who comes back after the parent leaves is locked
  out again.
- PIN state machine (`pinMode`/`pinStep`/`pinDigits`/`pinPending`): no-PIN →
  mandatory **setup** (new → confirm); has-PIN → **unlock** (verify, 3-strike
  lockout); panel card → **change** (current → new → confirm).
- PIN is stored as a **salted FNV-1a hash** (`nv_parent_pin`) — never the raw
  PIN — per-device only, and it never leaves the device. Proportionate for a
  curious-kid threat model.
- Full EN/BN parity (audit gate enforces it).
