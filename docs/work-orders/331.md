# Work order #331 — Kotha: story dedup + retention policy
> milestone: v26 — Kotha & adaptive · branch: `feat/issue-331`

## Goal
Prevent duplicate stories and prune old ones per a documented retention policy.

## Done when
- [x] Dedup key
- [x] Retention config
- [x] No data loss of active skills

## What shipped
- **Dedup key**: `LearningStory.uid` — the client's durable-outbox uid, now sent
  up with every story (client `api.ts` → `LearningStoryIn` → model). Server-side
  `record_stories` uses `INSERT … ON CONFLICT DO NOTHING` on `(kid_id, uid)`, so
  a replayed batch (lost ACK → same uid re-posted) is a silent no-op instead of
  a duplicate. `uid` is nullable + the constraint is `(kid_id, uid)`, so legacy
  NULL rows never collide (Postgres ignores NULLs in unique constraints). The
  POST response now reports `recorded` vs `duplicates_skipped`.
- **Retention config**: three settings (`config.py`, env `nv_*`):
  `kotha_retention_days` (90), `kotha_active_skill_days` (7),
  `kotha_max_stories_per_kid` (1000). `POST /api/v1/admin/stories/prune`
  (admin-only, idempotent) runs the policy and returns counts.
- **No data loss of active skills**: the age-prune deletes stories older than
  retention **only for skills NOT practiced in the active window** — an active
  skill keeps its full story history (the evolution of what the kid is working
  on right now). Then a per-kid volume guard trims to the most recent
  `max_stories_per_kid`, and the active tail is always the most recent, so
  active learning is never the overflow.
